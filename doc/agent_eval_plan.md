## 0. 给新 Codex 会话的强制执行指令

新会话开始时，必须先完整阅读本文件，再检查当前工作区代码。**本文件描述的是目标、约束和待核实事项，不代表所有建议模块已经存在。必须以工作区实际源码为准。**

### 0.1 工作原则

1.  **先审查，再修改。**
    先读取项目结构、README、入口脚本、配置、评测执行、裁判、报告、定时任务和测试代码，输出简短的现状映射与差距清单。未完成审查前，不得批量重构或新建大量文件。
2.  **增量改造。** 保留现有 CLI、评测采集、WebSocket、MCP
    校验、双裁判、报告、每日任务和企业微信通知能力；只有在确认存在明确缺陷且改动必要时才调整。
3.  **以真实评测为准。** UI
    不得使用假数据冒充真实评测结果。演示样例必须明确标注为样例，默认展示真实报告。
4.  **不改变业务语义。**
    不得擅自修改用例分类含义、通过阈值、评分公式、硬性规则、工具调用判断、报告字段含义。需要变更时先列出影响并请求用户确认。
5.  **优先复用现有依赖。**
    不得未经批准引入数据库、Redis、Celery、消息队列、前后端分离框架、容器编排或新的调度平台。
6.  **CLI 向后兼容。**
    现有命令及参数在未获批准前不得删除、改名或改变默认行为。UI
    与定时任务应尽量调用同一业务执行入口。
7.  **小步提交式工作。**
    每次只完成一个明确任务组；完成后运行相关测试，汇报文件变更、行为变化、验证结果和未解决风险，再进入下一组。
8.  **不要猜接口。**
    必须根据源码确认函数签名、配置结构、返回值和异常行为；不要生成"看似合理但无法运行"的调用。
9.  **安全优先。** 不得将 Token、API Key、企业微信 Webhook
    或真实用户对话写入源码、示例默认值、日志、报告模板或
    Git。不要输出密钥值。
10. **不要擅自扩大项目目标。**
    不做与本文件目标无关的架构升级、视觉重设计、抽象框架建设或"顺手优化"。

### 0.2 每轮 Codex 的工作协议

每轮按以下顺序执行：

1.  用 3--8 条说明本轮目标、会改哪些文件、不会改哪些内容。
2.  先检查相关代码与调用链，指出依据。
3.  给出最小改动方案；如果有多种方案，默认选择最简单、最兼容的方案。
4.  实施改动。
5.  执行可用的静态检查、单元测试或针对性验证；不能执行的测试要明确说明原因。
6.  汇报：
    -   修改文件与用途；
    -   关键行为变化；
    -   测试命令和实际结果；
    -   未完成事项与风险；
    -   下一步建议。
7.  未经用户明确同意，不要把"建议方案"当成已经批准的需求，不要自动进入下一阶段的大规模改造。

### 0.3 发现冲突时的优先级

发生冲突时按以下优先级处理：

1.  用户在当前会话明确确认的新决定；
2.  本文件中的项目边界、交付目标和强制约束；
3.  当前工作区真实源码及现有运行行为；
4.  README、注释和旧设计说明；
5.  Codex 自己的推测或常见最佳实践。

如果源码行为与文档描述不一致，先记录差异，不要默默选择一方并改变系统行为。

## 3. 总体技术设计

### 3.1 架构原则

推荐逻辑分层：

``` text
Streamlit UI
    |
    v
UI / Application Adapter
    |
    +--> Toy Profile Loader
    +--> Test Case Reader / Filter
    +--> Evaluation Service
    +--> Result / Report Reader
    |
    v
Existing Evaluation Core
    |
    +--> OTA / WebSocket Collection
    +--> Testers / MCP Validation
    +--> Prompt Template + Judge
    +--> Report Generation
    |
    v
reports/<toy_id>/...
```

每日定时入口仍可由现有 GitLab CI / `daily_run.py`
调用同一评测核心。不要让定时任务依赖 Streamlit 页面进程，也不要在
Streamlit 页面代码里复制一套评分逻辑。

### 3.2 建议新增的最小模块

先检查现有模块能否承担相同职责；只有确实缺失时才新建。

-   `ui/app.py`：Streamlit 应用入口。
-   `ui/pages/`：页面文件（可按实际复杂度决定是否拆分）。
-   `ui/services.py`：UI 到业务逻辑的薄适配层。
-   `ui/result_reader.py`：读取已有 JSON / Excel / Markdown
    报告并转换为展示数据。
-   `templates/template.md`：通用评估模板。
-   `templates/categories/`：只有在分类模板需要独立文件时才建立；否则可先在单一模板中按类型组织。
-   `config/evaluation_thresholds.json`
    或现有配置机制中的等价配置：存放分类阈值。不要在多个文件中重复定义同一阈值。
-   测试文件：根据仓库现有测试组织方式补充，不强制采用特定测试目录。

### 3.3 业务入口要求

UI
和每日任务必须调用同一评测业务入口。建议的抽象概念如下（名称仅供设计参考，必须依据源码确定最终签名）：

-   `load_toy_profile(toy_id)`：读取玩具配置。
-   `load_test_cases(toy_id)`：读取测试用例。
-   `filter_test_cases(cases, categories, ids)`：按类型或用例 ID 过滤。
-   `run_evaluation(request, progress_callback=None)`：执行一轮评测。
-   `read_evaluation_result(report_path)`：解析报告。
-   `build_summary(result)`：生成摘要指标。

不要因为上述概念而机械创建同名函数。如果现有代码已有等价实现，直接复用。

## 4. 功能一：动态工具描述与测试用例管理

### 4.1 工具描述数据源分级

实现前必须确认项目当前工具描述来源：

A. **当前本地文件模式**：`data/工具描述.txt` 或
`toys/<toy_id>/工具描述.txt`。本期应按所选玩具加载对应文件，并明确回退规则。

B. **MCP 实时发现模式**：如果项目已能连接 MCP Server
并获取工具清单，复用现有发现接口，读取工具名、描述和输入参数 Schema。

C.
**其他来源**：例如服务端接口或配置文件，必须先检查源码，不允许凭空新增外部接口。

第一版不强制从静态文本升级到实时 MCP
发现。优先做到"每次评测都加载所选玩具当前可用的数据源"，并将来源记录在评测元信息中。

### 4.2 玩具配置加载要求

-   UI 展示现有玩具列表，列表来源复用 `toy_profiles.py`
    或现有配置加载方法。
-   选择玩具后，展示其测试用例来源、工具描述来源以及是否存在必需配置。
-   文件缺失时显示明确错误，不应静默切换到另一个玩具的配置。
-   默认玩具 `default` 的现有路径和行为必须兼容。
-   对于本地工具描述文件，记录相对路径、读取时间；如实现成本低，可记录内容摘要（hash），以帮助复现。
-   不在页面中展示 Token、API Key 或其他敏感配置。

### 4.3 用例分类与筛选

已知类型包括：

-   基础问答
-   反向安全
-   情感交互
-   短期记忆
-   长期记忆
-   知识库
-   MCP 调用

类型名称、空单元格沿用上一行等 Excel
解析行为，必须复用现有解析逻辑或通过测试确认，不得自行重写成不兼容版本。

UI 最低要求：

-   显示用例总数。
-   按类型筛选。
-   查看用例编号、输入消息、预期结果、是否要求工具调用、工具名称。
-   支持选择全部用例或选中类别执行。
-   不要求本期直接在 UI 中增删改 Excel 数据。
-   如果提供编辑功能，必须独立确认保存规则、备份策略和并发覆盖风险；未经批准，默认只读。

### 4.4 验收标准

-   切换玩具后，显示的数据与该玩具配置一致。
-   缺少工具描述或 Excel 文件时有明确提示。
-   类别筛选结果数量正确。
-   筛选后的评测确实只运行所选范围，不只是改变页面显示。
-   不会意外修改原始 Excel 文件。
-   历史报告可识别本次使用的玩具与用例范围。

## 5. 功能二：`template.md` 与分类评估 Prompt

### 5.1 设计目标

把评估标准从 Python
代码中解耦出来。模板负责告诉裁判"如何判断"，代码负责准备输入、调用模型、校验输出、计算分数与阈值判断。

### 5.2 模板输入字段

根据实际评测数据提供字段，至少考虑：

-   `category`：用例类型。
-   `case_id`：用例编号。
-   `messages`：本次用例输入消息或消息序列。
-   `expected_result`：预期结果 / 通过标准。
-   `actual_response`：实际回复。
-   `tool_calls`：实际工具调用记录。
-   `expected_tool`：预期工具（若适用）。
-   `expected_tool_arguments`：预期参数语义（若适用）。
-   `category_rubric`：该类型评分标准。
-   `score_range`：0--1。
-   `output_schema`：裁判必须返回的 JSON 结构。

只注入该类型确实需要的字段；对缺失字段要有安全、明确的处理方式。模板变量应采用安全的模板替换机制，不得将任意内容当作可执行
Python 代码。

### 5.3 模板文件组织

首选简单方案：

``` text
templates/
└── template.md
```

模板文件内按类型定义评分规则，或在同一模板中根据 `category_rubric`
注入分类规则。

只有在分类规则已较稳定且单独文件明显提高维护性时，才拆成：

``` text
templates/
├── template.md
└── categories/
    ├── qa.md
    ├── safety.md
    ├── emotion.md
    ├── memory.md
    ├── knowledge.md
    └── mcp.md
```

不要在没有必要时同时维护一套总模板和多套重复的完整
Prompt。公共规则应只定义一次，分类差异单独定义。

### 5.4 评分输出契约

建议裁判输出可解析 JSON，字段可与当前项目报告兼容：

``` json
{
  "score": 0.85,
  "reason": "回答符合预期，关键信息完整",
  "issues": []
}
```

要求：

-   `score` 必须是有限数值，且满足 `0 <= score <= 1`。
-   不接受缺失分数、NaN、Infinity 或超出范围的分数。
-   `reason` 应能说明主要判分依据。
-   `issues` 可以为空数组；若现有代码不适合该字段，可在本期不强制落库。
-   `passed` 由程序依据阈值计算，不依赖裁判自由输出的 `passed`。
-   如果现有模型响应带有 Markdown
    代码围栏，应根据现有解析方式兼容；解析失败时返回明确的评分错误。
-   不应通过把无效分数强行截断到 0 或 1 来掩盖模型输出问题。

### 5.5 模板版本与复现

每份评测结果应尽量记录：

-   模板文件路径；
-   模板版本或内容摘要；
-   评分模型名称；
-   评分规则版本；
-   用例类型；
-   分类阈值；
-   数据集/用例来源。

短期内不要求建设完整模板版本管理平台。内容摘要、文件名和阈值快照足以作为
MVP 的可追溯基础。

### 5.6 验收标准

-   不同类型能够使用不同评分标准。
-   修改模板无需修改核心 Python 代码。
-   模板文件不存在或字段缺失时有明确错误。
-   对裁判无效输出不会生成伪造的业务评分。
-   双裁判仍按既有配置运行。
-   报告能看到评分结果与判分理由。

## 6. 功能三：0--1 评分与分类阈值

### 6.1 核心概念

必须区分：

1.  **原始裁判分数**：每个裁判返回的 0--1 分数。
2.  **综合分数**：依据已确认的综合规则计算。
3.  **通过阈值**：按用例类型配置的最低通过分。
4.  **用例状态**：通过、业务不通过、评分失败等离散状态。
5.  **整体通过率**：统计口径必须明确，不能将评分失败混入普通业务失败。

### 6.2 评分计算约束

当前 README 描述的基线是：两个裁判均可用时取平均分，平均分 `>= 0.7`
判通过。改造后允许不同类别配置不同阈值，但不要同时擅自更改双裁判聚合算法。

推荐的计算步骤：

1.  调用启用的裁判。
2.  校验每个裁判分数。
3.  按当前既定规则计算综合分。
4.  根据用例类型读取阈值。
5.  若评分有效且综合分达到阈值，则状态为 `passed`；否则为 `failed`。
6.  若评分服务不可用、超时、响应无法解析或分数无效，则状态为
    `judge_error`，不参与普通业务通过率分母，单独统计。

**双裁判部分失败的处理必须检查现有代码并明确决策。** 不要让 Codex
自行决定是用单裁判分数、判评分失败，还是继续采用现有策略。如果当前已有明确行为，本次保持；若没有，则先报告给用户确认。

### 6.3 分类阈值配置

可使用单一配置源，例如：

``` json
{
  "thresholds": {
    "基础问答": 0.70,
    "反向安全": 0.90,
    "情感交互": 0.75,
    "短期记忆": 0.80,
    "长期记忆": 0.80,
    "知识库": 0.80,
    "MCP调用": 0.90
  }
}
```

**以上数值仅为示例初值，不是已经确认的业务标准。**
必须在启用前由用户或业务负责人确认。Codex
不得把示例值当成最终验收规则。若来不及确认，保留原有 `0.7`
默认阈值，并将分类阈值功能实现为可配置能力；不要擅自提高安全或 MCP
阈值。

### 6.4 指标统计定义

建议报告提供：

-   `case_count`：选入评测的用例总数。
-   `passed_count`：业务通过用例数。
-   `failed_count`：有效评分下的业务不通过用例数。
-   `judge_error_count`：评分失败用例数。
-   `evaluated_count`：获得有效业务评分的用例数。
-   `pass_rate`：`passed_count / evaluated_count`；当
    `evaluated_count == 0` 时应显示为不可计算，而不是 0%。
-   `average_score`：有效综合分的平均值；无有效分数时不可计算。
-   `category_metrics`：每类用例的数量、通过数、业务失败数、评分失败数、通过率和平均分。

必须在 UI 中解释评分失败与业务失败不同，避免管理者误读指标。

### 6.5 硬性规则

对于 MCP
调用等场景，现有程序可能已经执行工具名称或调用结果的规则校验。保留并核实这些规则，不得让综合语言评分覆盖关键硬性失败。

如果硬性规则要影响最终状态，必须在报告中记录失败原因和规则来源；不得仅在
UI 上把通过改成不通过，而不修改底层结果语义。

### 6.6 验收标准

-   所有有效分数均在 0--1 范围内。
-   分类阈值从单一配置源读取。
-   修改阈值后，下一次评测使用新值，历史结果保留当次阈值。
-   `passed` / `failed` / `judge_error` 统计互斥且口径清晰。
-   无有效评分时不会出现除零错误。
-   现有双裁判平均分行为（在两裁判都成功的情况下）有测试覆盖。
-   旧报告读取失败时 UI 给出提示，不应崩溃。

## 7. 功能四：定时任务、手动触发与报告推送

### 7.1 本期触发方式

MVP 仅要求：

1.  CLI 手动执行；
2.  Streamlit 页面手动触发；
3.  现有 GitLab CI / `daily_run.py` 每日定时执行；
4.  评测结束后生成报告；
5.  如果现有配置已启用，继续推送企业微信。

"自动触发机制"在本期定义为可复用统一执行入口，并保留后续接入事件触发的扩展空间，不代表本期建设通用规则引擎。

### 7.2 统一执行入口

-   UI 不得复制 `daily_run.py` 的评分逻辑。
-   `daily_run.py` 不应依赖 Streamlit 运行。
-   如果现有 CLI
    入口只能通过命令行调用，短期可封装子进程执行，但必须安全传参、捕获退出码和日志，并处理超时。
-   如果评测逻辑已经可以通过 Python
    函数调用，优先直接调用现有函数，避免重复加载配置或运行两套逻辑。
-   每日定时任务与 UI 必须使用同一套模板、阈值与报告生成逻辑。

### 7.3 运行状态

最小状态集合：

-   `pending`：等待执行（仅在确实存在排队时使用）；
-   `running`：执行中；
-   `succeeded`：执行成功并生成结果；
-   `failed`：执行流程异常或整体任务失败；
-   `cancelled`：只有实现了取消能力时才使用。

单条用例的 `judge_error` 不等同于整个任务
`failed`。任务是否整体成功，应根据执行流程是否完成、报告是否生成等明确规则判断。

### 7.4 任务元信息

在不引入数据库的前提下，优先在报告或轻量 JSON 元信息中记录：

-   `run_id`；
-   `trigger_type`：`manual_cli` / `manual_ui` / `scheduled`；
-   `toy_id`；
-   选择的用例类型或范围；
-   开始与结束时间；
-   任务状态；
-   报告路径；
-   模板摘要、阈值快照（如果实现成本可控）。

避免创建复杂的任务持久化系统。若只用内存记录任务，必须明确重启后历史任务状态不会保留，历史记录应从报告目录读取。

### 7.5 Streamlit 长任务注意事项

-   评测可能持续数分钟，不得假定同步请求能立即返回。
-   第一版可使用受控的线程或子进程方式，具体选择根据现有执行入口和
    Streamlit 行为确定。
-   不得因页面重绘导致同一评测被重复启动。
-   不允许两个任务同时写入同一个报告文件。
-   对于暂不支持并发的版本，应明确限制为单任务执行，并在 UI
    中禁用重复启动按钮。
-   日志需要脱敏，不能把 Token、API Key 或 Webhook 写入页面。
-   不能假装有实时进度：如果引擎无法报告进度，只展示真实状态、最近日志和完成结果。

### 7.6 报告与通知

-   优先复用 `report.py` 和 `notify_wecom.py`。
-   通知失败不应删除已生成的评测报告。
-   报告生成失败应作为任务错误清晰呈现。
-   不得把 API Key、设备 Token、Webhook
    或未经检查的敏感对话内容发送到非预期目标。
-   保持已有 GitLab CI 环境变量机制，不在仓库里添加真实凭证。
-   修改 `.gitlab-ci.yml` 前先理解现有执行条件、Runner 和 schedule
    行为，避免改变生产每日任务。

## 8. Streamlit UI 范围与交互要求

### 8.1 页面范围

建议 MVP 为三个核心页面，可根据实现简化为多页或单页 Tab。

#### 页面 A：评测总览

显示：

-   "开始评测"按钮。

默认只读，不在本期实现完整 Excel 在线编辑器。

#### 页面 C：执行与结果

显示：

-   当前任务状态；
-   开始时间、结束时间；

-   用例明细、原始回复、裁判分数、理由、工具调用结果；

如果页面刷新后状态丢失，允许从报告目录恢复已完成任务的结果；不要承诺内存任务能跨进程重启恢复。

### 8.2 UI 技术约束

-   使用 Streamlit；不引入 Vue、React 或独立前端构建系统。
-   复用当前 Python 环境和现有依赖。
-   仅在需要时新增 `streamlit` 及必要的展示依赖，并记录到
    `requirements.txt`。
-   不把业务逻辑放在页面组件中。
-   不在 Streamlit Session State 中存储长期唯一的任务事实；Session State
    仅作为页面交互状态。
-   页面输入必须验证，文件路径不能接受任意不受控路径。
-   真实评测必须由明确的用户操作触发，不得页面加载即自动跑测。
-   若页面使用缓存，不能缓存动态评测结果而导致展示旧数据。
-   所有按钮都必须有真实行为，不能只是 UI 装饰。

### 8.3 启动方式

由 Codex 根据仓库环境补充实际启动命令。建议最终 README 说明：

-   安装依赖；
-   配置环境变量；

-   Streamlit 启动方式；
-   报告输出目录；
-   每日任务如何运行；

## 9. 测试与质量保障

### 9.1 先保护已有行为

改造前记录可运行的基础命令和已有报告样例。任何无法在当前环境执行的集成测试，都应在交付报告中明确标注，不能说"测试通过"。

  测试类别   测试内容                     预期结果
  ---------- ---------------------------- --------------------------

  配置加载   不存在的玩具                 清晰错误，不静默回退
  用例读取   正常 Excel                   用例数量与类型正确
  用例读取   缺少文件 / 工作表 / 必填列   明确提示
  类型筛选   选择某一类型                 只选择该类型用例
  工具描述   切换玩具                     加载对应工具描述
  模板       模板文件存在                 成功渲染所有必要字段
  模板       模板缺失 / 占位字段缺失      明确失败，不输出伪分
  评分       有效分数 0、0.7、1           正确接受
  评分       负数、大于 1、NaN、缺失      判为评分错误

  双裁判     两裁判有效                   保持既有综合规则
  双裁判     一个或两个裁判失败           按经确认的现有策略处理
  统计       评分失败用例                 单独统计，不混入业务失败
  统计       没有有效分数                 不除零，不显示误导性 0%
  报告       JSON / Excel / Markdown      保留现有产物和核心字段
  UI         点击启动                     触发真实评测
  UI         重复点击 / 任务运行中        不产生重复写入或重复执行
  定时       手动执行 `daily_run.py`      现有任务流程正常
  通知       Webhook 不可用               报告仍保留，通知错误可见
  安全       日志与错误提示               不泄露密钥

### 9.3 回归验证

在有可用环境变量和可访问待测设备的前提下，至少执行一次真实评测。建议选择少量代表性用例覆盖：

-   基础问答；
-   记忆类；
-   MCP 工具调用；
-   评分服务失败或无效响应的错误路径（可用 mock
    测试，避免故意影响真实服务）。

不要把真实 API
调用作为每个单元测试的前置条件。评分解析、阈值计算、统计逻辑应优先用可重复的单元测试覆盖。

## 11. Codex 必须遵守的技术约束

### 11.1 架构约束

-   不重写现有评测核心。
-   不在 UI 中复制评分、采集或报告逻辑。
-   不引入不必要的抽象层、工厂体系、插件框架或通用工作流引擎。
-   不为了"架构整洁"大规模移动或重命名文件。
-   不把 `daily_run.py` 变成 Streamlit
    的内部调用模块；应复用核心服务或最薄的适配层。
-   不假设所有评测过程都能提供精确百分比进度。
-   不承诺本期支持多用户并发与分布式执行。

### 11.2 依赖约束

-   先检查 `requirements.txt`，再添加依赖。
-   UI 只引入 Streamlit 及确有必要的轻量依赖。
-   不引入数据库、Redis、Celery、FastAPI、Vue、React，除非用户明确批准。
-   新增依赖需要说明用途、替代方案和对环境的影响。
-   不擅自升级现有依赖到不兼容的大版本。

### 11.3 配置约束

-   评分阈值只能有一个权威配置源。
-   评分模板只能有一个明确的加载路径与回退规则。
-   玩具配置必须复用现有 `toy_profiles.py` 约定。
-   不将密钥写入配置样例或 UI 默认值。
-   对默认配置的更改必须检查 CLI 与定时任务影响。
-   不在 UI 页面、`judge.py`、`report.py` 中重复硬编码阈值。

### 11.4 数据与报告约束

-   不覆盖原始测试用例文件。
-   不擅自修改既有报告字段含义。
-   新字段优先向后兼容；如必须变更，应同时处理旧报告读取。
-   评分失败单独统计。
-   历史报告应保留当次阈值、模板或可追溯摘要，避免用新配置解释旧结果。
-   不在 UI 中构造假数据填充空图表。

### 11.5 安全约束

-   所有敏感凭证继续通过环境变量或现有安全配置机制提供。
-   错误日志必须脱敏。
-   不在 UI 中显示完整设备 Token、API Key、Webhook。
-   不默认把用户对话内容发送到新的外部服务。
-   报告下载只允许读取应用指定的报告目录，不能接受任意文件路径。
-   对路径、用例编号、模板字段等输入进行必要验证。

### 11.6 代码质量约束

-   先遵循现有项目风格，不进行无关格式化。
-   函数职责清晰，避免 UI 文件承载所有逻辑。
-   新增业务分支应有测试或明确的手动验收步骤。
-   不删除"看起来没用"的旧逻辑，除非确认其无调用并获用户批准。
-   不虚构测试结果；未执行的测试明确写出。
-   修改后检查 `git diff`，确保没有密钥、临时文件或大批无关改动。

# 17. Streamlit Web UI 详细产品需求与交互规范（Codex 实施基线）

> 本节是 Streamlit UI 的详细需求基线。若前文 UI 描述比较概括，以本节的页面职责、字段、交互、状态和验收标准为准；本节不得覆盖前文“不得重写核心评测引擎、保持 CLI 兼容、不得擅自扩大范围”等全局约束。

> **重要：** 这里规定的是产品行为和验收目标，不代表当前源码已提供对应数据字段或 API。Codex 必须先核对真实代码；若某字段当前无法获取，应明确说明并提出最小兼容方案，不得用假数据伪装实现。

## 17.1 UI 目标、用户与设计原则

### 目标用户

- **部门领导 / 老板：** 快速理解评测覆盖范围、总体效果、风险及最近一次运行情况。
- **研发人员：** 配置评测范围、触发运行、查看单条用例和工具调用细节、定位评分或业务失败。
- **评测维护者：** 维护玩具配置、理解工具描述来源、检查用例分类和评分规则是否生效。

### UI 的核心任务

UI 必须形成如下闭环：

`选择玩具 → 查看工具和用例 → 配置评测 → 启动真实评测 → 观察运行状态 → 分析汇总结果 → 下钻失败用例 → 查看/下载报告`

用户不应为了完成上述流程而必须回到命令行手动拼参数。CLI 仍需保留，作为兼容入口和自动化执行入口。

### 设计原则

1. **结果可信优先于视觉效果。** 所有指标必须来自真实报告或真实任务状态；没有数据时显示空态，不生成示例数字。
2. **先总览，再下钻。** 先呈现结论，再允许用户查看类别和单条用例。
3. **配置透明。** 每次评测应能看出使用了哪个玩具、哪些用例、哪个模板、哪些阈值和哪个评分模型（仅显示非敏感标识）。
4. **状态清晰。** 区分任务执行状态与单条用例评分状态，不能把“评分服务异常”混为“Agent 业务失败”。
5. **渐进增强。** MVP 优先只读管理、真实执行和结果分析；不在本期建设复杂的在线数据编辑器。
6. **复用现有逻辑。** 页面只负责展示、收集参数和调用服务，不复制采集、MCP 校验、裁判评分或报告生成逻辑。

## 17.2 全局导航与页面关系

MVP 必须提供四个清晰的功能入口：

1. **评测总览**：默认首页，回答“系统最近运行如何、有没有风险”。
2. **用例与工具管理**：回答“评测什么、工具信息从哪里来、有哪些用例”。
3. **评测配置与执行**：回答“本次怎么评、启动后运行到哪一步”。
4. **结果分析**：回答“结果如何、哪些用例失败、为什么失败”。

建议使用 Streamlit `st.navigation` / `st.Page`（需先核实 Streamlit 版本支持情况），或使用当前版本支持的多页机制。若项目环境不支持，不要为了导航升级大量依赖，采用兼容的侧边栏选择即可。

### 全局侧边栏最低要求

- 应用名称：`Agent 评测工作台` 或与项目现有命名一致的名称。
- 当前选择的玩具 ID / 名称。
- 页面导航。
- 配置或数据源状态提示：正常、缺少配置、读取失败。
- 当前版本不要求登录、角色权限、多人协作或复杂设置页。

### 跨页面状态传递

- 用户在“用例与工具管理”选择的玩具，可通过 `st.session_state` 作为页面交互状态传递到“评测配置与执行”。
- Session State 仅用于当前浏览会话的 UI 选择，不作为任务持久化来源。
- 评测启动后，任务 ID、最终状态和报告路径必须来自执行层真实返回值或落盘元信息，不能仅存在于页面变量中。
- 刷新页面后，可以通过扫描报告目录恢复已完成报告列表；不能承诺内存中的运行任务在进程重启后仍可恢复。

## 17.3 页面一：评测总览（Dashboard）

### 17.3.1 页面目标

这是老板和部门领导打开系统后首先看到的页面。应在 10 秒内让用户回答：最近有没有运行评测、覆盖多少用例、通过情况如何、评分服务是否出错、哪里需要关注。

### 17.3.2 页面布局

**区域 A：页面标题与快捷操作**

- 标题：`评测总览`。
- 简短说明：显示最近评测情况与历史报告概览。
- 主操作按钮：`新建评测`，跳转到页面三或切换至“评测配置与执行”。
- 次操作：`刷新数据`，重新扫描现有报告/任务数据，不触发评测。

**区域 B：最近一次评测摘要**

展示最近一次可读取的评测记录：

- 玩具名称 / ID；
- 运行时间；
- 触发方式（CLI、Web UI、定时任务，只有实际记录了该字段才展示）；
- 任务状态；
- 报告入口。

若没有报告，显示明确空态：`暂无评测记录，请先运行一次评测。` 并提供 `开始评测` 按钮。不得显示虚构的“最近一次成功”。

**区域 C：关键指标卡片**

至少展示：

- 本次用例总数；
- 业务通过数；
- 业务通过率；
- 业务失败数；
- 评分失败数；
- 平均综合分（如果有有效评分）。

口径必须遵循第 6 节：通过率分母为有效评分用例数；评分失败单独统计；有效评分数为 0 时显示 `—` 或 `不可计算`，不能显示成 0%。

**区域 D：分类质量概览**

按用例类型展示表格，至少包含：

- 用例类型；
- 用例数；
- 通过数；
- 业务失败数；
- 评分失败数；
- 通过率；
- 平均分；
- 本次使用阈值（如果报告保存了阈值快照）。

点击某一类型时，应进入结果分析页面并携带该类型筛选条件。若 Streamlit 页面参数传递实现复杂，可先在结果页面提供相同筛选能力，但不能让用户误以为表格行可点击却没有行为。

**区域 E：最近评测记录**

从报告目录或现有历史记录来源读取最近若干条记录，展示：

- 时间；
- 玩具；
- 用例数（如果可从报告解析）；
- 通过率（若可计算）；
- 任务状态；
- 查看结果入口。

历史报告字段不完整时，应展示已知信息，并对无法计算的字段显示 `—`，不能因一份旧报告缺字段导致整个首页崩溃。

**区域 F：最近需要关注的问题**

可选但推荐：展示最近一次评测中的评分失败或业务失败用例，字段包括用例 ID、类别、状态、简短原因。MVP 若时间不足，可先提供“查看失败用例”入口，不必实现复杂告警排序。

### 17.3.3 交互规则

- `刷新数据` 只刷新数据，不启动评测。
- `新建评测` 进入页面三，并尽量保留当前选择的玩具。
- `查看结果` 进入页面四并定位到对应报告。
- 指标卡片不得触发隐式业务操作。
- 页面初始化不得自动启动评测、发送企业微信通知或调用裁判模型。
- 首页扫描报告目录时应处理文件不存在、JSON 损坏、旧版本字段缺失等情况。

### 17.3.4 验收标准

- 没有报告时能正常显示空态。
- 有真实报告时指标与报告数据一致。
- 通过率分母和评分失败统计口径正确。
- 点击新建评测能进入配置页面。
- 点击查看结果能打开正确报告。
- 刷新页面不触发新评测。

## 17.4 页面二：用例与工具管理

### 17.4.1 页面目标

让用户确认当前评测的数据来源、玩具对应的工具描述和测试用例范围，并能按类别检查用例内容。MVP 以**读取、筛选、预览、选择执行范围**为主，不实现复杂在线编辑器。

### 17.4.2 区域 A：玩具选择与数据源信息

页面顶部提供玩具选择控件，选项必须来自现有 `toy_profiles.py` 或项目已有配置加载逻辑，不得在 UI 中硬编码一份重复列表。

选择玩具后显示：

- 玩具 ID / 名称；
- 测试用例文件路径（相对路径即可）；
- 工具描述来源路径或来源类型；
- 文件是否存在、读取是否成功；
- 读取到的用例总数；
- 工具描述是否为空。

若工具描述来源为本地文件，明确显示 `本地配置文件`；若项目确实实现了 MCP 实时发现，才显示 `MCP 动态发现`。不得把静态文本文件读取包装成“实时工具发现”。

如果所选玩具缺少必需文件：显示错误原因、缺失文件路径和建议操作；不允许静默回退到其他玩具的数据。

### 17.4.3 区域 B：工具清单

以可读的列表、表格或展开面板展示当前玩具的工具信息。实际可展示字段由数据源决定：

- 工具名称；
- 工具描述；
- 输入参数 / JSON Schema（如果来源提供）；
- 数据来源；
- 最近读取状态（若可获取）。

如果现有工具描述只有纯文本，则原样展示文本并明确其来源，不强行解析出不存在的结构化字段。

MVP 不要求 UI 在线编辑工具定义，也不要求从未知的外部 MCP Server 自动发现工具。若当前项目没有动态发现能力，本期只实现“按所选玩具动态读取对应工具描述文件”。

### 17.4.4 区域 C：用例分类统计与筛选

筛选控件至少包括：

- 用例类型：支持全部类型或单个/多个类型；
- 用例 ID：如果用例有稳定 ID，支持按 ID 搜索；
- 关键词：可选，搜索输入内容或预期结果；
- `重置筛选` 按钮。

页面展示当前筛选后的数量，例如 `显示 12 / 48 条用例`。分类统计必须由真实读取的用例计算，不要从固定数字生成。

类型映射必须基于现有 Excel 解析和 `testers.py` 里的类型处理方式。Codex 应先确认实际类型名和别名；若存在中文类型名差异，建立集中映射，不得在多个页面各写一份类型判断。

### 17.4.5 区域 D：用例列表与详情

列表至少显示：

- 用例 ID / 行号；
- 类型；
- 输入消息或消息摘要；
- 预期结果摘要；
- 是否要求工具调用（仅在数据实际提供时展示）；
- 预期工具名称（仅在数据实际提供时展示）。

点击某条用例或使用 `查看详情` 后，应能看到完整输入、预期结果、工具要求和源文件信息。长文本可使用 `st.expander` 或详情区域展示，避免表格横向过宽。

若当前 Excel 没有稳定用例 ID，可以使用经确认的行号/组合标识作为展示 ID，但必须保持同一轮运行中稳定，并在文档中说明；不要自行修改原始 Excel 结构。

### 17.4.6 区域 E：选择用例并进入评测

MVP 必须支持：

- 选择全部用例；
- 按类别选择用例；
- 可选地选择筛选结果中的用例；
- 点击 `使用当前范围创建评测` 后进入页面三，并将玩具和选定范围带过去。

如果 Streamlit 多页状态传递无法可靠保存复杂的用例对象，只传递玩具 ID、类别和用例 ID 列表等轻量标识；执行时由服务层重新加载数据并校验。不要将整份 Excel DataFrame 作为唯一的任务输入来源。

### 17.4.7 写入/编辑范围

本期默认只读，不做新增、删除或修改 Excel 的功能。除非用户明确批准，不得通过页面把修改直接覆盖原始测试用例文件。

### 17.4.8 验收标准

- 玩具列表来自现有配置加载逻辑。
- 切换玩具后工具描述和用例数据同步变化。
- 缺少文件时有明确错误，不会错误回退。
- 类型筛选结果和数量正确。
- 选择的评测范围会真实传递到执行服务。
- 用例详情展示的内容与 Excel 原始数据一致。
- 不会修改原始 Excel 文件。

## 17.5 页面三：评测配置与执行

### 17.5.1 页面目标

这是核心操作页面。用户能够理解本次评测将使用什么配置、选择评测范围、启动真实评测，并在运行期间看到可信的状态反馈。

### 17.5.2 区域 A：评测目标与范围

配置项：

- 玩具选择：默认沿用前一页的选择；允许修改，但修改后必须重新校验用例范围。
- 用例范围：全部用例、按类别、指定用例 ID（只实现项目能可靠支持的范围）。
- 当前预计执行用例数。
- 运行模式：仅提供现有 CLI 已支持的模式，例如 `fast`；不得凭空增加不存在的模式。
- 可选输出路径：默认遵循现有报告目录与命名规则。MVP 优先不开放任意文件系统路径输入。

在点击启动前，显示本次配置摘要：玩具、用例数量、类别、工具描述来源、评分模板和阈值配置来源。

### 17.5.3 区域 B：评分配置

页面展示本次实际使用的评分配置：

- 通用模板路径（例如 `templates/template.md`，以实际实现为准）；
- 分类评分规则是否成功加载；
- 裁判模型名称（只显示模型标识，不显示密钥）；
- 双裁判启用状态；
- 分类阈值表；
- 当前阈值来源与是否为默认值。

MVP 建议评分配置以只读展示为主，配置变更通过受控配置文件完成。除非用户明确要求在线修改并确认保存规则，本期不实现 Web 表单直接写入模板或阈值文件，以避免误操作和配置竞争。

若模板或阈值配置无效，启动按钮必须禁用或在点击时阻止执行，并显示可操作的错误信息。不能在配置缺失时静默使用硬编码值，除非这属于已确认的兼容回退规则。

### 17.5.4 区域 C：启动前校验

点击启动前至少校验：

- 玩具配置存在；
- 测试用例文件可读；
- 选择范围非空；
- 必需的工具描述可读取（如果该类型评测依赖工具描述）；
- 评分模板可读取；
- 阈值配置有效；
- 必要环境变量存在（只能提示变量名，不显示值）。

错误应按项目可理解的方式列出，并阻止不合法任务启动。不得把所有错误都折叠成 `运行失败`。

### 17.5.5 区域 D：启动与防重复

主按钮：`开始评测`。

点击行为：

1. 进行启动前校验；
2. 生成本次运行 ID（如果现有执行器已生成则复用）；
3. 调用统一执行服务；
4. 显示任务状态；
5. 运行中禁用重复启动，避免同一配置被误触发多次；
6. 执行结束后展示结果摘要并提供跳转到页面四的入口。

点击按钮必须触发真实评测，不得只生成静态结果。页面重新运行或重新渲染不得重复触发任务。若 Streamlit 版本行为导致回调重复，应通过明确的状态锁/运行 ID 保护。

### 17.5.6 区域 E：运行状态与日志

任务状态至少包含：

- `pending`：只有实际存在等待队列时使用；
- `running`：执行中；
- `succeeded`：执行流程完成且报告成功生成；
- `failed`：执行流程异常或未能生成必要结果；
- `cancelled`：只有实际实现取消能力时才显示。

状态展示字段：

- 运行 ID；
- 开始时间；
- 当前状态；
- 已完成用例数 / 总用例数（仅当执行层能提供真实进度时展示）；
- 最近日志或错误摘要；
- 报告路径/入口。

如果执行引擎没有逐用例进度回调，只能展示真实的 `running` 状态和最近日志，不得用定时增加的百分比伪装进度。第一版可以不支持取消；未实现时不要显示取消按钮。

### 17.5.7 长任务执行要求

Codex 必须根据现有执行器选择最小可靠方案：

- 如果评测函数可直接调用，评估 Streamlit 同步执行是否会造成不可接受的页面阻塞；
- 如果采用线程或子进程，确保异常、退出码、日志和报告路径可以被主页面读取；
- 不引入任务队列系统；
- 通过状态锁防止重复运行；
- 每次任务使用独立报告文件名或目录，避免覆盖；
- 如果 MVP 限制单任务并发，UI 必须明确提示“当前已有评测运行，请等待完成”。

### 17.5.8 完成后的操作

任务完成后提供：

- `查看结果`：跳转页面四并定位本次运行；
- `下载报告`：只在文件存在且路径位于允许的报告目录时显示；
- `重新运行`：作为新的运行创建新 run ID，不覆盖上一轮结果。

### 17.5.9 验收标准

- 配置摘要与实际执行参数一致。
- 无效配置不能启动任务。
- 点击启动能执行真实评测。
- 页面重绘不重复执行。
- 运行状态来源真实，进度不造假。
- 重复启动被阻止或安全隔离。
- 完成后能跳转结果页并查看本次运行。

## 17.6 页面四：结果分析

### 17.6.1 页面目标

页面需要同时满足管理者看结论和研发人员定位问题两种用途。首先显示整体结果，然后按类型、状态和单条用例逐层下钻。

### 17.6.2 区域 A：选择报告 / 运行记录

- 默认打开从页面三跳转过来的本次运行结果。
- 可从现有报告目录选择历史报告。
- 报告列表应展示文件时间、玩具 ID、格式和可解析的运行信息。
- 旧报告缺少新字段时，尽量展示可读取的字段；无法计算的指标显示 `—`。
- 报告不存在、损坏或格式不支持时显示明确错误，不应导致整页崩溃。

### 17.6.3 区域 B：整体结论与关键指标

显示：

- 玩具与运行 ID；
- 运行时间和触发方式（若有）；
- 用例总数；
- 有效评分数；
- 通过数、业务失败数、评分失败数；
- 业务通过率；
- 平均综合分；
- 本次评测状态；
- 报告生成状态。

建议在顶部提供一句由确定性规则生成的结果摘要，例如：`本次共评测 40 条用例，30 条通过，7 条业务失败，3 条评分失败。` 不要调用额外 LLM 生成结论，以免引入延迟和不确定性。

### 17.6.4 区域 C：分类结果

表格字段：

- 类型；
- 用例数；
- 通过数；
- 业务失败数；
- 评分失败数；
- 通过率；
- 平均分；
- 实际使用的通过阈值（若报告保存了阈值快照）。

允许用户按类别筛选下方用例明细。图表属于增强项：如果时间不足，先把数据表做准确；不为了图表引入新的依赖。

### 17.6.5 区域 D：用例明细表

筛选项：

- 全部 / 通过 / 业务失败 / 评分失败；
- 用例类型；
- 用例 ID 或关键字（如果存在稳定标识）。

表格至少展示：

- 用例 ID；
- 类型；
- 最终状态；
- 综合分；
- 阈值；
- 预期结果摘要；
- 实际回复摘要；
- 简短判分理由。

对旧报告中不存在的字段显示 `—`，不推断或伪造实际回复、工具调用或评分理由。

### 17.6.6 区域 E：单条用例详情 / 诊断

用户选择一条用例后，展示可用的完整明细：

1. 用例基本信息：ID、类别、输入、预期结果；
2. Agent 实际回复；
3. 评分结果：每个裁判的分数、综合分、阈值、最终状态；
4. 判分理由与问题列表；
5. MCP / 工具调用：工具名称、参数、结果或异常（仅当采集数据存在）；
6. 相关错误信息；
7. 本条用例是否触发硬性规则，以及规则失败原因（如果现有数据能提供）。

详情区域可以使用展开面板或独立详情区。不得默认把所有长文本全部铺开，避免页面过长。不要将隐藏的推理链或模型内部思维作为产品展示内容；只展示实际采集的消息、工具调用记录和裁判给出的判分理由。

### 17.6.7 区域 F：报告下载

- 提供现有 JSON、Excel、Markdown 文件下载入口。
- 只允许下载应用指定报告目录内的文件。
- 不接受来自 URL 参数或用户输入的任意文件系统路径。
- 文件缺失时显示 `该格式报告不存在`，其他格式仍可使用。
- 下载操作不得重新运行评测。

### 17.6.8 结果统计规则

严格遵循第 6 节定义：

- `passed_count`：有效评分且通过阈值的用例数；
- `failed_count`：有效评分但未通过的用例数；
- `judge_error_count`：评分过程失败或评分输出无效的用例数；
- `evaluated_count`：获得有效综合分的用例数；
- `pass_rate = passed_count / evaluated_count`，当分母为 0 时不可计算；
- `average_score` 仅对有效综合分计算。

硬性规则对最终状态的影响必须沿用核心评测逻辑，不能仅在 UI 层重新判定。

### 17.6.9 验收标准

- 结果页数据与所选报告内容一致。
- 分类汇总与用例明细统计一致。
- 评分失败单独展示，不混入业务失败。
- 选择类别/状态能正确筛选用例。
- 能查看单条用例的可用诊断信息。
- JSON、Excel、Markdown 文件存在时可下载。
- 缺字段或损坏报告不会导致页面崩溃。

## 17.7 四页面之间的端到端验收流程

Codex 必须至少完成以下手工验收流程，并在汇报中逐项报告结果：

1. 打开总览页，没有历史报告时显示空态。
2. 进入用例与工具管理，选择一个实际存在的玩具。
3. 确认工具描述来源、用例总数和分类统计与本地文件一致。
4. 选择一种用例类型，检查筛选结果正确。
5. 从当前选择进入评测配置页面，确认玩具与用例范围已传递。
6. 检查模板、阈值和裁判配置状态。
7. 点击开始评测，确认真实评测被触发且没有重复启动。
8. 等待执行结束，确认状态和报告路径真实。
9. 进入结果分析，确认总数、通过数、业务失败数、评分失败数口径正确。
10. 筛选一条失败用例，打开详情，查看实际回复、判分理由和工具调用（若有）。
11. 下载至少一种真实报告。
12. 回到总览刷新数据，确认新报告出现在最近记录中。
13. 使用原有 CLI 入口再执行一次安全的验证命令，确认 CLI 兼容。
14. 确认 UI 页面加载、切页、刷新均不会自动触发评测或发送通知。

## 17.8 页面需求与实现优先级

### P0：本期必须实现

- 四个页面可访问，导航清晰。
- 页面二可选择玩具、查看工具描述、按类型查看/筛选用例。
- 页面三可配置范围、启动真实评测、显示状态。
- 页面四可显示真实汇总、用例明细、评分失败，并下载已有报告。

## 17.9 Codex 实施顺序与每轮输出要求

7. **端到端验收：** 按 17.7 的流程验证。

每个阶段结束后，Codex 必须提供：

- 实际修改的文件清单；

- 使用的数据来源与字段映射；
- 测试命令和真实输出；
- 未实现项及原因；
- 与本节需求不一致的地方；
- 下一步最小任务建议。

不得只汇报“页面已完成”或“测试通过”，必须给出可核验的证据。未执行的测试必须标记为“未执行”，不能写成通过。
