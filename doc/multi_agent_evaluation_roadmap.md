# 多 Agent 评测平台扩展方案与实施路线

> 整理日期：2026-10-28  
> 文档性质：需求梳理、架构建议与分阶段实施方案。  
> 阅读对象：测试人员、产品负责人、开发人员。  
> 状态说明：现有版本已完成的功能与后续待开发内容分开列出。本文件不是新增功能已实现的声明；文中的接口、目录和配置均为设计示例。

## 1. 先明确这次扩展要解决的问题

现有平台主要评测公司的玩具助手。后续希望在同一平台配置自家与竞品 Agent，选择一组相同用例，分别执行，使用统一规则评分，最后比较结果。

未来还要覆盖两类对象：

- **Chat Agent**：主要通过对话完成问答、咨询、情感交互等任务。
- **Work Agent**：通过操作工具、文件或系统完成工作，例如生成分析表、修改代码、处理网页任务。

本次讨论确定的方向是：**统一管理被测对象，统一组织评测任务，通过适配器处理接入差异，通过验收器处理结果验证差异。**

平台不要求知道 Agent 内部如何规划、调用什么模型、如何组织工作流。但需要能提交输入，确定执行状态，并获取足以评分的结果或证据。

## 2. 盘点现有基础，避免重新建设

### 2.1 现有版本已经具备什么

根据当前代码与完成记录，已有以下基础：

| 能力 | 当前情况 | 扩展时的处理方式 |
|---|---|---|
| 自家玩具接入 | OTA 获取连接信息、WebSocket 对话、MCP 消息处理 | 封装为现有设备适配器，保留原链路 |
| 用例管理 | Excel 用例、七类场景、范围选择、增删改、备份恢复 | 继续使用，逐步增加稳定用例 ID 和版本 |
| 工具描述 | 本地来源和远程 MCP 定义发现 | 保留；不能把工具发现当作 Agent 对话入口 |
| 评分 | 分类模板、双裁判、0–1 数值规则、分类与单条基准、MCP 硬规则 | 复用通用部分，设备专项规则按能力执行 |
| 报告 | JSON、Excel、Markdown、分类统计、单条诊断 | 扩展被测对象信息和横向对比 |
| 页面 | 总览、用例与工具、执行、结果分析 | 逐步增加 Agent 配置中心与对比视图 |
| 触发 | 手动、每日计划、文件／CLI 事件 | 后续统一创建多 Agent 总任务 |
| 运行保障 | 独立进程、日志脱敏、配置快照、设备互斥 | 保留，并扩展子任务隔离与资源配额 |

现有实现的具体完成与验证记录见 [功能与 UI 完成清单](completion_status.md)。其中记录本地 40 项测试通过；真实设备、裁判 API、通知及部署环境的最终回归仍需真实凭据。**这些验证不代表本文件提出的多 Agent 或 Work 功能已经通过测试。**

### 2.2 当前尚未具备的扩展能力

- 通用 Agent 配置中心及跨协议适配器契约。
- 一个总任务选择多个 Agent，以及各自独立的子任务管理。
- 多 Agent 的同题对比和共同能力统计。
- Work 任务的输入资产、隔离环境、产物收集及验收器。

这些属于后续开发范围，不能仅靠修改现有玩具配置实现。

## 3. 第一步：定义评测对象，先把名称说清楚

“评测豆包”这类说法还不足以确定接入方案。需要明确具体对象：

| 对象 | 实际评测内容 | 需要确认的入口 |
|---|---|---|
| 某个基础模型 | 模型在给定提示词、上下文和工具条件下的能力 | 模型 API 与模型标识 |
| 某个官方助手 API | 接口开放的助手能力 | 官方助手 API、功能开关及权限 |
| 某平台上搭建的具体 Agent | 提示词、知识库、工作流、工具共同构成的应用效果 | 已发布的 Agent API 与授权 |
| App／网页中的实际产品 | 用户实际使用时的产品行为 | 对应官方入口，或经许可的界面评测方式 |

**模型 API 结果不能直接标注为该厂商 App 的完整产品表现；一个聊天分享链接也不等于可调用 API。**

豆包方向可进一步调研官方模型接口、豆包助手 API；若对象是扣子上的智能体，则核查其 API 发布与访问权限。具体可用能力、限额、版本和授权以接入时官方文档与账号实际权限为准：

- [豆包助手官方文档](https://docs.volcengine.com/docs/ark/doubao-assistant?lang=en)
- [扣子发起对话文档](https://docs.coze.cn/developer_guides_chat_v3)

上述链接是接入调研参考，不表示平台已经实现对应适配器，也不承诺任意豆包／扣子对象都能调用。

### 3.1 每个新对象先填写接入调查表

| 调查项 | 要记录的内容 |
|---|---|
| 身份 | 厂商、产品、Agent／模型标识、负责人、版本 |
| 测试目的 | 通用能力对比，还是完整产品体验比较 |
| 入口 | 官方文档、地址、协议、网络要求 |
| 授权 | API 权限、密钥获取方式、允许测试的范围 |
| 生命周期 | 同步、流式、异步任务；如何判断结束和取消 |
| 会话 | 创建、隔离、上下文、重置、长期记忆清理方式 |
| 能力 | 文本、图片、工具、知识库、文件、工作环境等 |
| 可观察性 | 回答、工具记录、任务状态、产物、用量是否可取得 |
| 资源 | 并发、限流、超时、费用、输入／输出大小限制 |

如果只有界面，没有可调用接口，先明确人工结果导入或经许可的界面自动化路线。配置中心不能凭空获得访问能力，也不应默认通过抓取私有接口完成接入。

## 4. 第二步：定义最终业务流程与页面布局

### 4.1 统一业务流程

```text
配置中心登记 Agent，并验证连接与能力
                    ↓
准备用例、输入资料、评分及验收规则
                    ↓
创建总任务：多选 Agent + 选择用例 + 确认执行条件
                    ↓
固定本次配置快照，为每个 Agent 建立独立子任务
                    ↓
适配器执行，收集回答／产物／执行证据
                    ↓
程序验收 + 裁判大模型评分
                    ↓
各 Agent 独立报告 + 总任务横向对比报告
```

Agent 通常返回回答、状态和产物。**评测报告由本平台生成，不要求外部 Agent 返回统一报告。**

### 4.2 页面建议

| 页面 | 核心操作 |
|---|---|
| Agent 配置中心 | 新建、编辑、禁用、连接测试、查看能力与配置版本 |
| 用例与规则 | 管理 Chat／Work 用例、数据集版本、模板、阈值、验收条件 |
| 创建评测任务 | 多选 Agent、选择用例、显示兼容性、配置裁判及预算 |
| 执行监控 | 总任务与子任务状态、日志、错误、取消、重跑 |
| 结果与对比 | 单体报告、同题回答／产物对比、分类表现、覆盖率 |
| 触发与运行配置 | 手动／每日／事件入口、限额和运行状态 |

这些是业务模块，不要求一次性拆成六个独立页面。可在现有 Streamlit 导航中分阶段增加，避免首期界面过重。

## 5. 第三步：设计统一适配层

### 5.1 三层职责

```text
评测业务层：任务、用例、评分、报告、页面、触发
                           ↓
统一执行契约：能力、会话／任务、输入、状态、结果
                           ↓
具体适配器：自家设备、通用模型 API、厂商专有 Agent API
```

业务层不能到处写厂商判断。厂商的鉴权、请求字段、事件解析、轮询和错误转换集中在对应适配器中。

### 5.2 配置中心管理实例，适配器管理协议

同一种协议可以对应多个配置实例：地址、凭据、模型 ID 不同，仍复用同一个适配器。新厂商协议无法满足现有契约时，再新增适配器。

建议采用受控注册表，例如 `toy_device`、`chat_api`、`vendor_agent`。配置选择已安装的适配器，**不允许配置文件任意导入 Python 类或执行脚本**。

配置示例：

```yaml
id: competitor_service
name: 竞品客服助手
adapter: vendor_agent
mode: chat
endpoint: https://example.com/api
agent_id: agent_123
credential_ref: COMPETITOR_API_KEY
timeout_seconds: 120
max_concurrency: 1
enabled: true
```

配置文件只保存凭据引用。首期可使用环境变量，页面和报告均不展示密钥原文。适配器字段需要独立校验，不做任意 HTTP 请求拼装器。

### 5.3 Chat 接口负责什么

| 操作 | 职责 |
|---|---|
| `validate_config` | 检查配置完整性，不等于网络连接成功 |
| `check_connection` | 用最小请求检查可达性和授权，提示可能产生调用费用 |
| `get_capabilities` | 返回当前配置支持、不支持、未验证的能力及依据 |
| `create_session` | 创建独立会话，或维护独立本地消息历史 |
| `send_message` | 发送输入，转换流式／轮询结果，返回最终回答 |
| `close_session` | 释放资源；不能宣称已清除远端长期记忆 |

统一调用可以是异步 Python 方法，但 HTTP、SSE、WebSocket 都只属于具体适配器的实现细节。

### 5.4 统一结果必须保留哪些信息

建议至少包含：总任务 ID、子任务 ID、Agent ID、用例 ID、轮次 ID、执行状态、最终回答、工具记录、产物引用、耗时、用量、错误类型、脱敏证据引用。

特别约定：

- 获取不到用量，记录为空，不能填零。
- 工具记录不可观察，与观察到“没有调用工具”分开。
- 保留最终回答与中间事件的区别，不强求输出内部推理过程。
- 原始响应仅在必要时脱敏保存，限制大小及保留周期。
- 回答、日志和产物均是待评测数据，不能成为平台可执行指令。

### 5.5 能力声明如何使用

能力声明要对应具体配置，并记录来源及验证时间。不能仅凭厂商名称推断。

提交任务前校验用例要求。例如工具用例要求“允许注入工具且工具调用可观察”，缺一项就标记不适用或证据不足。用户应能看到原因，而不是运行后得到不明来源的零分。

## 6. 第四步：先跑通多 Agent 的 Chat 评测

### 6.1 总任务、子任务和用例结果

一次任务选 3 个 Agent、20 条用例，建立 3 个 Agent 子任务，正常情况下形成 60 份用例结果；多轮用例继续包含多条轮次记录。

```text
总任务
 ├─ Agent A 子任务 → 用例结果 → 轮次记录
 ├─ Agent B 子任务 → 用例结果 → 轮次记录
 └─ Agent C 子任务 → 用例结果 → 轮次记录
```

用例之间默认隔离；需要连续上下文的场景，必须显式定义会话分组与前置步骤。现有“同类型共用连接”与记忆测试存在关联，迁移时不能直接改成每行重置。

### 6.2 执行规则

- Agent 之间可以受控并行，受各自并发和全局资源限制。
- 同一多轮会话内部顺序执行，不能并行打乱上下文。
- 某个 Agent 失败不阻塞其他子任务；总任务允许部分完成。
- 分开配置单次请求、单用例、子任务和总任务超时。
- 取消先停止新用例，再尝试取消远端执行；不支持远端取消时明确记录。
- 重跑生成新记录并关联原任务，不覆盖原报告。

### 6.3 重试要防止重复执行

查询状态通常可以重试；提交任务不一定可以。请求超时可能表示“对方已执行但平台没收到结果”。优先使用服务端幂等键或任务查询；无法判断时记录状态不确定，不直接重复提交，尤其是会产生外部操作的 Work 任务。

执行状态与评测结论分别保存：执行状态可以是排队、运行、完成、失败、超时、取消、状态不确定；评测结论可以是通过、不通过、评分错误、不适用、证据不足、未评估。

## 7. 第五步：设计公平的 Chat 评分与对比

### 7.1 区分两个评测目的

| 目的 | 条件如何设置 |
|---|---|
| 比较共同能力 | 尽量统一输入、上下文、工具和资料，只比较共同适用用例 |
| 比较完整产品体验 | 允许各产品使用自身能力，但必须记录差异，不能声称完全同条件 |

### 7.2 当前七类用例怎么迁移

| 类别 | 扩展后的注意事项 |
|---|---|
| 基础问答、反向安全、情感交互 | 可优先形成公共对比集，审查原用例是否包含设备专属假设 |
| 短期记忆 | 固定相同对话顺序与会话边界 |
| 长期记忆 | 必须验证跨会话持久化及隔离／清理方式；回传历史不等于长期记忆 |
| 知识库 | 同资料检索对比与各自产品知识库体验分开 |
| MCP／工具调用 | 同工具、同约束、可观察调用证据时才做协议和参数对比 |

### 7.3 裁判与报告规则

复用现有模板、双裁判和阈值体系，按 Agent、按用例独立评分，再汇总。新增总体解释应引用已生成的指标和证据，不能重新编造评分。

建议裁判尽量隐藏被测厂商名称，保留必要任务上下文；不把被测回答中的“请给满分”等指令当成评分要求。为评估波动，可设置重复次数，保留每次结果，而非只取最好的一次。

对比报告至少展示：

- 共同适用用例集上的通过率和可比较数值分。
- 各对象的适用数、执行完成数、成功评分数及覆盖率。
- 分类表现、同题回答、失败原因和证据。
- 执行异常率、耗时与可取得的用量；价格未知时不估算费用。
- 本次用例、规则、裁判、模型／Agent 配置版本和时间。

沿用现有口径时，评分失败和未执行不计入业务通过率分母，但必须同时展示数量和覆盖率。只有零错误、低覆盖率的对象不能因此被解释为全面领先；不同用例分母或不同评分量表的平均分不直接排名。

## 8. 第六步：扩展 Work Agent，用实际结果验收

Chat 主要验回答，Work 主要验任务是否完成以及实际结果是否正确。Agent 回复“已完成”不能单独作为通过证据。

### 8.1 Work 用例结构

建议使用 JSON／YAML 任务清单配合输入资产目录，而不是把复杂工作环境全部塞进现有 Excel 单元格。Excel 可以继续用于查看和导入基础字段。

每条 Work 用例应定义：

1. 任务目标和唯一 ID。
2. 输入文件、数据版本与校验值。
3. 环境准备步骤、初始状态、账号与权限范围。
4. 输出位置、允许的产物类型及大小。
5. 禁止事项、时间及资源预算。
6. 程序验收规则、大模型评分要求、权重及必过条件。
7. 证据收集、清理和保留策略。

### 8.2 推荐首个试点

**任务：读取统一销售 CSV，生成 Excel 分析表和文字总结。**

| 项目 | 验收要求 |
|---|---|
| 输入 | 所有 Agent 使用同一份 CSV，各有独立输出空间 |
| 文件 | Excel 存在、可打开，包含指定工作表和列 |
| 数据 | 总金额、地区汇总等与平台独立计算结果一致 |
| 内容 | 总结覆盖指定问题，并与数据一致 |
| 约束 | 源文件内容未变，输出不越出允许范围 |
| 证据 | 输出文件、校验结果、耗时、执行状态 |

该试点容易准备标准答案和程序校验，适合先验证完整链路；它不代表所有 Work Agent 都具备文件上传或产物下载接口，仍需先做能力检查。

### 8.3 任务型适配器

在共用配置、能力与结果模型基础上，增加 Work 生命周期：

```text
prepare_environment → submit_task → get_status／wait
                                      ↓
                       collect_artifacts → cleanup
```

可选 `cancel_task`；远端不支持时不能伪装已取消。输入上传、回调或轮询由适配器处理；回调接入后还需要鉴权、关联任务及防重复，首期可优先采用轮询。

Chat 与 Work 使用两套明确的执行接口，不设计一个所有方法都为空的万能类；同一个 Agent 实例可以声明同时支持两种模式。

## 9. 第七步：建立 Work 验收器和评分规则

适配器负责“怎么交互”，验收器负责“结果是否满足任务”。两者不要混在一起。

| 验收方式 | 示例 |
|---|---|
| 程序校验 | 文件格式、表格计算、数据库状态、接口状态、代码测试 |
| 大模型评估 | 总结是否准确完整、方案是否符合要求、内容表达质量 |
| 人工复核 | 争议、不可自动判定或影响较大的结果 |

### 9.1 0–1 评分示例

销售分析任务可以暂拟：数据正确性 50%、结构完整性 20%、分析内容 30%。**这只是方案示例，不能自动写成正式业务标准。** 权重、容差和通过基准需要按用例审定并版本化。

可配置必过条件，例如源文件不得修改。必过条件失败时任务判不通过，同时保留原始分项得分和原因，避免把所有信息压成一个零分。

某个必须评分项证据缺失时，标记证据不足或验收错误，不临时把它的权重分摊给其他项。人工评分要留审计记录，不覆盖原自动结果。

### 9.2 工作用例的环境要求

- 每次运行从相同初始快照开始，各 Agent 使用独立环境。
- 文件、代码、网页、业务系统分别选择适合的隔离方式。
- 测试会产生写操作时，使用受控测试数据及测试账号。
- 不直接执行 Agent 产出的任意代码；需要执行时在受限沙箱中运行。
- 平台限制产物路径、类型、数量和大小，收集前检查越界及符号链接。
- 环境准备和清理失败应记录为环境问题，不能误判 Agent 能力。

对于没有操作轨迹的黑盒对象，只评价能验证的最终结果。没有足够证据时，不能声称“从未访问过其他路径”等过程约束已通过。

## 10. 第八步：定义数据与存储，再开始开发

建议先统一以下数据对象，减少页面与执行代码互相牵制：

| 对象 | 主要内容 |
|---|---|
| Agent 配置 | 稳定 ID、适配器类型、参数、能力、凭据引用、修订号 |
| 用例版本 | 稳定 ID、模式、输入、会话分组、能力要求、规则版本 |
| 总任务 | Agent 列表、用例集、裁判与预算快照、汇总状态 |
| Agent 子任务 | 执行参数、会话／远端任务 ID、状态、时间和错误 |
| 用例执行记录 | 输入、回答／产物、事件证据、执行状态 |
| 评分记录 | 验收器／裁判版本、分项、结论、基准及原因 |
| 产物记录 | 相对路径、类型、大小、hash、来源与保留策略 |

现有 Excel 行号用于追溯，后续不能作为跨版本唯一标识，因为增删行会改变位置。新体系使用稳定用例 ID，保留原文件 hash、工作表和行号映射。

建议首期用 SQLite 保存任务元数据与状态，大文件和产物继续存目录；所有写入经统一存储层，避免 UI、worker 各自拼接文件。评估 SQLite 事务与并发写入方式，不把本地数据库部署到未经验证的共享盘。多机器协作再迁移服务端数据库和队列，不在首期直接引入完整分布式系统。

报告应包含 schema 版本。旧报告走兼容读取，新字段允许缺省；历史报告不能用最新配置重新解释。设备锁继续用于原设备资源，多 Agent 并发另外按账号、实例和环境限制，避免仅按 Agent ID 就绕过同设备互斥。

## 11. 第九步：对应当前代码制定改造边界

以下是建议职责映射，不是已新增的文件清单：

| 当前模块 | 建议改造方向 |
|---|---|

## 12. 第十步：按阶段实施，每阶段有可验收结果

### 阶段 0：确认范围，冻结现有基线

- [ ] 完成现有真实设备与裁判接口回归，保留基线报告。
- [ ] 确认一个可调用的外部对象及权限，不提前假设竞品名单。
- [ ] 选择一组公共文本用例，明确哪些原用例依赖设备。
- [ ] 明确共同能力比较与产品体验比较的任务类型。

**交付物：接入调查表、首批公共用例、现有功能基线。**

### 阶段 1：打通两种协议的单 Agent 执行

- [ ] 定义适配器契约、能力模型、统一结果及错误分类。
- [ ] 封装现有设备适配器，保留原 CLI 和页面行为。
- [ ] 实现一种已确认的外部 API 适配器。
- [ ] 增加配置中心、连接测试及配置校验。
- [ ] 用统一入口分别跑通自家与外部对象。

**验收：同一公共用例可对两种协议运行并评分；旧设备流程回归通过；未支持能力可明确识别。**

### 阶段 2：多 Agent 任务与比较，形成第一版扩展 MVP

- [ ] 一个总任务创建多个 Agent 子任务。
- [ ] 实现隔离会话、受控并发、超时、取消与重跑。
- [ ] 每个 Agent 独立报告及总对比报告。
- [ ] 展示共同用例集、覆盖率、异常和统计口径。
- [ ] 每日与事件入口接入同一任务服务，保持旧格式兼容。

**验收：至少两个对象完成同批用例；其中一个失败时另一个正常出报告；刷新页面可恢复查看真实任务状态。**

### 阶段 3：Work 文件任务试点

- [ ] 定义 Work 用例、任务型适配器与产物契约。
- [ ] 准备销售 CSV、独立环境及程序标准答案。
- [ ] 跑通提交、等待、产物收集、验收、评分和报告。
- [ ] 实现源文件保护、产物范围限制及清理。

**验收：Agent 宣称完成但缺文件或数据错误时，平台能判失败；正确产物能通过；证据可下载追溯。**

### 阶段 4：按真实需求扩展

- [ ] 新增确定需要的厂商专有适配器。
- [ ] 按任务类型增加代码、网页或业务系统验收器。
- [ ] 按使用规模增加多人权限、任务队列、远端 worker 和存储治理。
- [ ] 根据实际报告校准裁判与用例，不以增加厂商数量替代评测质量。

**推进原则：先完成一个可重复、可验证的闭环，再扩大接入数量与任务类型。** 不建议首期同时实现所有协议、任意脚本配置、界面自动化和分布式调度。

## 13. 测试人员怎样参与每个阶段

测试人员不需要先掌握所有框架内部实现，可以先把任务定义和验收证据做扎实：

1. 确认每个被测对象到底是什么、要比较什么。
2. 为用例补齐输入、前置条件、预期结果和不适用条件。
3. 审核标准答案、阈值、权重与必过条件。
4. 准备正常、异常、边界和权限不足的样本。
5. 检查报告能否从结论追溯到具体回答／产物／验证证据。
6. 对争议用例人工复核，推动规则修订并保留版本。

开发人员主要负责适配器、执行编排、存储及校验器实现；业务负责人确认评测目标和标准。厂商访问权限、资源预算及真实测试窗口也需明确责任人。

### 最低验收场景

| 场景 | 平台预期表现 |
|---|---|
| 密钥错误、地址不可达 | 配置或执行错误，不生成虚假低质量得分 |
| 流式中断、缺少结束标志 | 标记未完整完成，保留部分证据 |
| 多轮测试 | 上下文连续，其他用例／Agent 不串会话 |
| 一个子任务失败 | 其他子任务继续，总任务展示部分完成 |
| 裁判超时或返回非法分值 | 评分错误，与被测 Agent 执行状态分开 |
| 不支持工具或证据不可见 | 不适用／证据不足，解释原因 |
| 重复触发、提交后超时 | 按幂等和不确定状态处理，避免重复副作用 |
| 运行中修改配置／用例 | 当前任务使用快照，新任务使用新版本 |
| Work 假完成 | 根据真实产物验收，不能只凭完成声明通过 |
| 读取旧报告 | 不崩溃、不用新规则改写历史结论 |

## 14. 开工前需要确认的决策

以下问题暂不替业务方做假设，进入对应阶段前确认即可：

| 待确认项 | 推荐起点 |
|---|---|
| 首个外部对象 | 选择有官方 API、权限明确、文档完整的对象 |
| 首批比较范围 | 先公共文本任务，后设备／知识库／记忆专项 |
| 首个 Work 类型 | CSV → Excel／报告的文件任务 |
| 部署范围 | 先单机受控并发，确认需求后再多机 |
| 凭据及访问 | 环境变量引用起步，多人使用前增加权限控制 |
| 预算与限额 | 显式设置任务规模、并发和调用预算，费用未知不承诺精确估计 |
| 评分标准 | 由业务和测试确认，示例权重不直接生效 |
| 产物保留 | 明确保留时间、下载权限和清理方式 |

## 15. 方案边界与共同结论

本次讨论形成的是可执行的扩展方向：

- 配置中心统一管理不同被测 Agent 实例，评测任务可多选。
- 适配器解决厂商协议差异，同协议复用，新协议按需开发。
- Chat 验回答及可观察行为；Work 验产物和实际任务结果。
- 裁判大模型是评分工具之一，确定性结果优先程序验证。
- 总任务汇总各子任务，但保留能力、条件、覆盖率和异常差异。
- 现有设备链路持续可用，按阶段迁移和回归，不一次性推倒重写。

本文件只落地方案与执行清单，不启动外部评测、不增加真实凭据、不自动启用调度，也不把后续开发项标记为完成。
